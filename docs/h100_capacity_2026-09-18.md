# H100 capacity and quota, measured 2026-09-18

The four long-context inference cells (`qwen7b_kv16k_b32`, `qwen1_5b_kv16k_b48`,
`qwen72b_kv16k_b24`, `qwen72b_kv4k_b48`) have been queued and unrun since
2026-09-17, blocked on H100. This records what is actually blocking them, because
"H100 quota" and "H100 capacity" are different problems with different fixes and
we had been treating them as one.

**Headline: quota is no longer the binding constraint anywhere we care about.
Capacity is. On-demand H100 is stocked out in every zone we hold quota in (34/34
zone-probes), while Spot has capacity in 15 of 33 zones.**

## How the quota is actually shaped

H100 does **not** have a per-accelerator quota. There is no
`NVIDIA-H100-GPUS-per-project-region` — the legacy `compute.googleapis.com`
region quotas stop at A100/L4, which is why `gcloud compute regions describe`
shows nothing for H100 and why the console is easy to misread. On-demand H100
lives in the Cloud Quotas API under:

    quotaId   GPUS-PER-GPU-FAMILY-per-project-region
    dimensions {gpu_family: NVIDIA_H100 | NVIDIA_H100_MEGA, region: <region>}

Spot is separate and conventional: `PREEMPTIBLE-NVIDIA-H100-GPUS-per-project-region`.

Two consequences:

* **Spot H100 quota is 64 in every region by default** — it applies to all 43
  locations with no per-region grant needed. We never needed to ask for it.
* **On-demand H100 quota defaults to 0**, so outside a granted region you cannot
  even attempt a provision, and "quota or stockout?" is unanswerable until the
  quota exists. That is why the requests below had to be filed before the
  capacity question could be asked.

Reaching the API at all needs `x-goog-user-project`; without it the call 403s
against Cloud Shell's own project with a misleading `SERVICE_DISABLED`.

## Capacity, measured not assumed

The API cannot answer "is there a machine free"; only a create attempt can. Each
probe created one VM and deleted it, with
`--max-run-duration=600s --instance-termination-action=DELETE` so a probe that
loses its supervisor removes itself rather than leaking an $88/hr node. Verified
afterwards: zero probe instances left standing.

**a3-highgpu-8g, STANDARD (on-demand) — 18 zones, 18 stockouts.**
us-central1{a,b,c} plus every zone of the 8 newly-granted regions
(asia-southeast1, europe-west1, europe-west3, europe-west4, us-east4, us-east5,
us-west1, us-west4) return `ZONE_RESOURCE_POOL_EXHAUSTED_WITH_DETAILS` with
`zonesAvailable: ''` — Google is not even suggesting an alternative zone.

**a3-megagpu-8g, STANDARD — 19 zones, 18 stockouts + 1 not-offered.**
The Mega pool (same 8×H100 80GB, 3200 Gbps networking) is no better.

**a3-highgpu-8g, SPOT — 33 zones, 15 available.**

| verdict | zones |
|---|---|
| AVAILABLE (15) | asia-east1-c, asia-northeast3-c, asia-south1-b, asia-south1-c, asia-south2-b, europe-west2-b, europe-west2-c, europe-west3-a, europe-west3-c, europe-west4-b, europe-west4-c, europe-west9-c, **us-central1-a**, **us-east4-a**, **us-east5-a** |

Note `us-central1-a`: **Spot has capacity in the same zone where on-demand is
exhausted.** The two pools are disjoint, so a Spot success says nothing about
on-demand and vice versa.

## What this means for the four queued cells

They were queued non-preemptible deliberately — Spot preemption is what killed
the 2026-08-20 TPU campaign three times in one night, and a 72B KV-cache cell is
long enough to be exposed. Options, in the order I would try them:

1. **`--provisioning-model=FLEX_START`** in a granted region. Flex Start queues
   for capacity and then runs uninterrupted for a bounded window, which is the
   shape of this workload (a few hours, then delete). It does not compete for the
   same immediately-available pool the STANDARD probes just found empty.
   `scripts/gcp/provision_ondemand_pair.sh:17` already documents the flags.
2. **Spot in us-central1-a / us-east4-a / us-east5-a**, accepting preemption.
   `launch_queue.sh` now has `STOP_WHEN_DONE` and `--instance-termination-action=STOP`,
   so a preemption costs the current cell, not the boot disk or the corpus. This
   is the only pool with capacity *right now*.
3. **Retry STANDARD on a schedule.** Stockouts of this kind clear in hours, and
   we now hold quota in 9 regions instead of 1, so a retry loop has 18 zones to
   sweep instead of 3.

Reproduce any of this with the probe in the session scratchpad (`h100_probe.sh`)
or re-derive the quota picture from the Cloud Quotas API as above.

## A100-80GB as the missing control (2026-09-21)

Section 33 found that the detector leans hardest on `mem_used_mb_*`, and that in
this corpus training sits at a median 14.2 GB while every vLLM cell sits at
74-79 GB because they all pass `--gpu-memory-utilization 0.9-0.92`. Section 31c
separately found that a threshold calibrated on one accelerator does not transfer
to another. Section 32d had to concede that the two are entangled: "some of the
family-level failure is hardware transfer, not workload transfer, and this design
cannot separate them."

**A100-80GB separates them.** It is the same memory per card as the H100 and a
different GPU, which completes a 2x2 the corpus has never had:

| | 80 GB per card | 40 GB per card |
|---|---|---|
| **H100** | existing corpus | — |
| **A100** | **a2-ultragpu-8g (queued 2026-09-21)** | running now on the a2-highgpu-8g pair |

* H100-80 vs A100-80 isolates the HARDWARE at matched memory.
* A100-80 vs A100-40 isolates MEMORY SCALE at matched hardware, and answers the
  question section 33 actually poses: is "nearly full card => not training" about
  the FRACTION an allocator holds, or about absolute gigabytes?

**No cell modifications are needed, and that is the point.** The 80 GB cell set
queued for A100 is byte-identical to the H100 set -- same 20 cells, same
`--gpu-memory-utilization` sweep, same TP/PP, same model sizes. Only the machine
type changes. (The A100-40 pair needed its own `infermem_qwen72b_u45/u65/u85` and
smaller training batches precisely because 40 GB cannot hold the 80 GB sweep;
that difference is the experiment, not an inconvenience.)

### Quota

A100-80GB quota was 16 in us-central1 and 0 everywhere else. Four requests filed
2026-09-21 were **all auto-granted within ~3 minutes**, so we now hold 16 in
us-central1, us-east4, us-east5, europe-west4 and asia-southeast1 -- exactly one
2-node pair each.

### Capacity

`a2-ultragpu-8g` STANDARD is stocked out in both us-central1 zones (probed
2026-09-21, create-and-delete, `ZONE_RESOURCE_POOL_EXHAUSTED_WITH_DETAILS`), the
same picture as H100. Queued instead via the Flex Start MIG resize-request
fan-out across all seven zones that offer the hardware: us-central1-a/c,
us-east5-a/b, us-east4-c, europe-west4-a, asia-southeast1-c.

Cost when granted: a2-ultragpu-8g is ~$41/h on demand, so a pair is ~$82/h
undiscounted (Flex Start is cheaper), and a 20-cell x 2-rep pass is ~6-8 h.
